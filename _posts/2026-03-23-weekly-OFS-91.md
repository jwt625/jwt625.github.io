# Reflections on coding in experimental physics

been generating a lot if code with the new claude, and occasionally I would get flashbacks to high school, when I was getting to know code for the first time with pascal and matlab, while at the time my major interest was turning from chemistry to math.. it was so much struggle to read matlab's confusing documentation, and the gui was so confusing I would never close the "getting started? check our documentation" prompt in the command window because I was afraid of not being able to find link to the docs later.
   - and also flashbacks to learning java for the sake of learning java during undergrad while doing physics most of the time, I remember the first time when I switched from eclipse to intellij, and the auto completion blew my freaking mind that I had to record a video of it in action with my phone.
   - like look at this! You can generate the get and set methods for your properties automatically! It's insane!
   ![20260310_094457_0.jpg](/assets/images/2026/20240627_20260322/20260310_094457_0.jpg)
   - However, my actual coding skills dropped going into grad school, a lot of "dirty" work to interface with the nasty real world, and you end up writing a lot of scripts and a lot of thrown away code. The most complex coding projects were probably one of my first big experiment runs, and ironically one of my last experiment runs. The first one was a series of measurements where I had to automate some fiber to chip alignment, followed by pure optical characterizations, followed by some optoelectronic characterizations, and the whole workflow needs to be robust enough to run few hundred times over night against a handful of edge cases. It was a big messy satisfying script.
   - and the last one involved sending and detecting pulses with accurate timing, while operating and stabilizing a few dozens of optoelectronic and microwave components. It's much more complex in both the construction of the experiment setup as code, as well as the execution procedure itself as code, but still mostly simple OOP + giant set of long scripts.
   - on the design and simulation side, things are a bit more interesting, you are constructing your chip as code, it is very descriptive, and with more layers of abstractions as the components and cells mature, and as the circuits and chips grow in complexity. It's also getting closer to a service, as the codebase is shared across more people. But very little actual components a software service would have, very little log, no usage tracking, very little metrics, little RBAC, outputs not really organized, and would you believe it's a struggle to get people to use git, and based on my interactions with friends in similar fields, it's like this across the board.
   - the simulation is probably the most intellectually demanding work. Laying out a chip is pretty much a braindead activity, you got this shape and this shape into this component that component, and it goes here there, and you wire them up (well there are a lot of gotchas too). Actually design is pretty braindead too, except the initial part where you were trying to figure out what to design and why. There's inverse design but it's niche, otherwise nothing has more than a dozen parameters, and you can sweep or use fancier tricks like genetic algorithms for optimization. I would almost always kick off a run before going to sleep, and woke up with a mesh error, or with a regret of not running a smaller test batch first. The code is again just a set of scripts to kick of these runs, and to turn the .mat files into .fig plots that you would almost never bother to open so you learnt to also save them as png files. No centralized management or viz. If the runs were bigger, I probably would've got more exposure to slurm etc.
   - i'm falling asleep. hopefully continue tmw.
